# 商品の階層と、このリポジトリの対象

更新日: 2026-08-18

## 階層

```text
上位の総合管理ツール
├─ 歌推しページ      ← このリポジトリ（ColorSing_LP）
├─ SLT
├─ 特典管理
├─ イベント
└─ 将来のOBS / Stream Extension
```

上位の総合管理ツールは、顧客アカウント、契約、複数機能、管理導線を統合する層である。**このリポジトリのリファクタリングで作っているのはその層ではない。**

## 歌推しページ

外部へ公開される顧客ごとのページで、月600円案の主対象。今の ColorSing_LP がこれにあたる。`fanpage-create.html` は「歌推しページを作る」画面であり、DAP（`onboarding.html`）は歌推しページの初期設定を案内する。

## 売る商品

商品は2つ。実装は `src/productization/plans.js`。

| ID | 名前 | 状態 | 作れるもの |
| --- | --- | --- | --- |
| `fanpage` | 歌推しページ | 販売中 | 歌推しページ |
| `pro` | Pro | 準備中（`coming_soon`） | 歌推しページ ＋ SLT等 |

Proはまだ出さない。準備中の商品は `/products` に申し込みボタンを出さず、金額が
設定されていても進ませない。それでもカタログとして2商品を扱うのは、歌推しページ
専用の構造で固定すると、Proを足すときに獲得導線と利用権の設計をやり直すことに
なるからである。Proの内訳は未確定なので、決まっていないものを箇条書きにして
約束したように見せない。

利用権（entitlement）はこの商品IDでサーバー側が判定する。**ブラウザが持っている
「購入済み」を認可の根拠にしない。** 決済事業者は未確定のままProvider境界に置く。

```text
Stripe webhook ─┐
手動付与        ├→ サーバー側 entitlement → tenant作成
Membership付与 ┘
```

## 名前の扱い

「Portal」は上位の総合管理ツールを指す語として温存する。歌推しページを指して Portal と呼ばない。実装でも次の名前を使う。

| 概念 | 使う名前 |
| --- | --- |
| 獲得導線の状態 | `fanpage_not_created` / `fanpage_provisioning` / `fanpage_ready` |
| オンボーディングの手順 | `fanpage_created` |
| 作成ロジック | `src/productization/fanPageCreation.js` |
| 作成画面 | `src/fanpage/FanPageCreateApp.jsx` / `fanpage-create.html` |
| 利用者向けの表示 | 「歌推しページを作成する」「歌推しページを準備しています」「歌推しページの作成が完了しました」 |

内部の概念名と利用者向けの言葉は分ける。統合基盤の人物マスタは `supporters`（支援者）だが、配信者から見た相手は**リスナー**なので、画面には「リスナー」と出す。「支援者」は固い。

| 内部の概念名 | 利用者向けの表示 |
| --- | --- |
| `supporters` / supporter | リスナー |
| Portal（上位の総合管理ツール） | 歌推しページとは別物。歌推しページを指してPortalと呼ばない |
| DataSource | 表に出さない。「リスナー情報を設定しましょう」のように作業で示す |

## 新規顧客と既存顧客のデータ経路

```text
既存顧客
Google Sheets → 互換維持・安全な移行 → Central DB / 管理画面

新規顧客
管理画面 → Central DB → 歌推しページ
```

Google Sheetsは**既存顧客を壊さず移行するためのlegacy data source**であり、新規顧客の標準運用ではない。新規顧客へテンプレートSheetのコピーやURL登録を求めない。上位指示書は、Spreadsheet ID・「リンクを知っている全員」・Drive画像公開設定を、消すべき顧客の認知負荷として名指ししている。新しい商品で旧運用を再生産しない。

| | 新規顧客 | 既存顧客 |
| --- | --- | --- |
| `resolveTenantKind` | `new` | `legacy` |
| 正規データソース | Central DB | Google Sheets |
| DAPの手順 | リスナー情報 | データ管理方法・データ接続 |
| Sheets→DB移行 | 対象外 | 対象 |

判定は `src/productization/tenantKind.js`。スプレッドシートIDを持つ設定だけをlegacyとするため、既存顧客の手順と表示は変わらない。

`DataSource` は内部実装の概念なので利用者へ選ばせない。DAPには「データ管理方法を選択してください」ではなく「リスナー情報を設定しましょう」のように、利用者が実際にやりたい作業を出す。Portalを顧客向けに出していたのと同じ誤りを繰り返さない。

Sheetsが残るのは、既存顧客のdry-run・mirror・semantic diff・shadow read・切替という移行経路と、将来のインポート／エクスポートである。これらは移行・互換の機能であって、新規オンボーディングの必須工程ではない。Sheets→DBのmigration DAPは既存顧客専用として別に扱う。

## 共通基盤へ寄せている理由

将来、上位の総合管理ツールから歌推しページを作成・管理できるようにするため、Provisioning と DataSource の境界を共通基盤へ寄せている。歌推しページ側の実装がその境界を直接持たないのは、上位層が同じ境界を使えるようにするためである。

現時点で上位層の実体はこのリポジトリに無い。存在する前提で接続しない。
